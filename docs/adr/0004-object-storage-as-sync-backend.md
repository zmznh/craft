# ADR-0004：对象存储（OSS/COS）不作为同步后端

- 日期：2026-10-01
- 状态：**已否决**（作为同步后端）／**已采纳**（作为备份目的地候选）
- 相关：ADR-0001（正文单一真源）、ADR-0003（元数据增量同步）

## 背景

用户在成本敏感的上下文中提出：改用阿里云 OSS 是否可以实现多端实时云同步。
本项目的同步需求有三类数据，它们的传输形态差异很大，不能一概而论。

## 判定

| 数据 | 能否走对象存储 | 原因 |
|---|---|---|
| 文档正文（Yjs 二进制） | **可以** | 不可变 blob，CRDT 可乱序合并，append-only 更新日志成立 |
| 白板（tldraw-sync） | **不行** | 依赖 WebSocket 房间内存态，对象存储无长连接 |
| 目录 / 搜索 / 标签 | **受限** | 能存 blob，但对象存储无 SQL，检索与排序能力全部丧失 |
| 凭证签发 | **不行** | AK/SK 不能进浏览器，STS 临时凭证需要一个签发端点（即服务端） |

## 正文走 OSS 在技术上如何成立

Yjs 是 CRDT，因此"对象存储 + 覆盖写"有一个特性可以救场：**分片永不覆盖**。

```
客户端编辑 → Yjs update → 节流 3-5s → PUT y/{docId}/{clientId}-{seq}.bin（只新增，不覆盖）
其他端     → 轮询 list 前缀 → 下载未见过的分片 → Y.mergeUpdates 合并进本地 YDoc
定期       → compaction：N 个分片合并为 checkpoint，删旧分片
```

乱序、重复、延迟到达的分片都能正确合并，这是 CRDT 的性质，不依赖服务端事务。

**但绝不能做覆盖写。** A 上传覆盖了 B 的分片，而 B 已在本地回收了那份更新历史时，
B 的编辑**永久丢失**——CRDT 只在"两个更新最终都到达同一处并合并"时才安全。

## 否决理由

### 1. 变更检测只能靠轮询，而轮询的流量成本被严重低估

对象存储没有订阅/推送机制。要感知"哪些文档变了"，只能周期性 `ListObjects`。

按本项目规模实测估算（1000 篇文档，约 60 字节/key）：

| 轮询间隔 | list 响应体（约 100 KB/次） | 月流量 | 外网下行费（约 ¥0.5–1/GB） |
|---|---|---|---|
| 2 秒 | 43,200 次/天 | **约 130 GB/月** | 约 ¥65–130/月 |
| 10 秒 | 8,640 次/天 | 约 26 GB/月 | 约 ¥13–26/月 |
| 60 秒 | 1,440 次/天 | 约 4.3 GB/月 | 约 ¥2–4/月（但已不"实时"） |

请求费本身可忽略（¥0.01/万次，百万次约 ¥1），**流量才是大头**。
请求费便宜容易让人误判整个方案便宜。

优化手段（前台才轮询、分片索引、增大间隔）能压低，但每一项都在用"实时性"换钱。

### 2. 现有 VPS 方案边际成本为零，OSS 方案是净增支出

VPS 已在付费，客户端与数据库同机走本地回环，**零流量费、毫秒级延迟**。
换 OSS 不仅新增流量账单，还把本地回环变成公网往返。

### 3. 它解决不了三类数据里的两类

白板与凭证签发仍然需要常驻服务端。既然服务端无法去掉，
"用 OSS 省掉服务器"这个前提就不成立——省不掉，只多了一笔流量费。

### 4. 会连带摧毁已完成的收敛工作

ADR-0001 刚刚把正文收敛为"服务端派生的单一真源"，依赖服务端在落库时
渲染 `Document.content`。纯 OSS 方案没有服务端，派生、版本快照、
`plainText` 索引全部要搬到客户端重做。

## 已采纳的部分：作为备份目的地

对象存储在**备份**（低频、大块、无需检索）场景下非常合适，这正是当前
CloudBase 存储承担的角色。相比 CloudBase 个人版订阅（¥19.9/月），
对象存储按量付费对单人用量接近零成本。

切换时需注意：

- **备份是写入多、读取极少**，不触发上面的轮询流量问题
- 下载恢复时才产生外网下行流量，单次几十 MB，可忽略
- 服务端（VPS）持有凭证即可，**不存在浏览器直连问题**

## 决策

1. 同步架构**不变**：正文继续 Hocuspocus，白板继续 tldraw-sync，元数据继续 REST 轮询。
2. 对象存储**仅用于备份**。若要替换 CloudBase 存储，需另行评估并改造
   `deploy/backup/crafty-backup.sh` 的上传目标（当前用 `tcb storage upload`）。
3. 若将来要真正去掉常驻服务端，唯一自洽的形态是"整个知识库建模为一个 Yjs 文档 +
   客户端全文索引"，代价是搜索能力重做、白板功能放弃，本 ADR 不推荐。
